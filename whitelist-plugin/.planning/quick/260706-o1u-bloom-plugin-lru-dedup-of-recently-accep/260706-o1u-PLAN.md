<objective>
Add a bounded LRU dedup of recently-ACCEPTED event IDs to the bloom plugin so that duplicate copies of an already-accepted event (arriving from many of the ~174 upstream relays) are rejected instead of re-accepted. This stops the same event from being queued repeatedly in strfry's in-memory WriterPipeline, which is the amplifier behind the relay-fan-in OOM (measured 84% of writer-checked events were duplicates).

Purpose: Nostr event IDs are content hashes — identical ID means a byte-identical event, so rejecting the copy is always safe (strfry would discard it as a dup on commit anyway). Rejecting early keeps it out of RAM.

Output:
- New `pkg/dedup` package: a small hand-rolled, dependency-free LRU keyed on the decoded 32-byte event ID.
- `RejectDuplicate` output constructor (empty msg — strfry logs blocked events only when msg is non-empty; at ~47 dup/sec a per-dup log line would recreate a past disk-fill incident).
- Dedup gate inside `RouterHandler.Handle`'s accept branch, opt-in per plugin via a `WithDedup` setter (so `cmd/router` and existing tests are untouched).
- Config knob `dedup_capacity` (default 100000) on `BloomConfig`; `cmd/bloom` wires it in.

Concurrency: the stdin event loop in `cmd/bloom/main.go` (`runEventLoop`) processes lines sequentially in a single goroutine, so `Handle` — and therefore the LRU — is single-goroutine. The LRU is lock-free with a documented single-goroutine invariant, matching the existing lock-free pattern in `pkg/bloomgate/checker.go`. Do NOT add a mutex.

Out of scope (do NOT touch): gen-relay-fan-in-config.sh, docker-compose files, strfry configs, `cmd/router`, anything outside `whitelist-plugin/`. Deployment to the strfry host is out of scope.
</objective>

  <files>/Users/g/git/deepfry/whitelist-plugin/pkg/dedup/lru.go, /Users/g/git/deepfry/whitelist-plugin/pkg/dedup/lru_test.go</files>
  <behavior>
    - New(0) or New(negative) returns a usable LRU whose SeenOrAdd always reports "new" (never a dup) and never grows — a disabled LRU.
    - New(cap) with cap>0: first SeenOrAdd(k) returns false (new) and records k; a second SeenOrAdd(k) returns true (dup).
    - Eviction: fill to capacity with distinct keys, add one more distinct key; the oldest inserted key is evicted — SeenOrAdd(oldest) now returns false again (was forgotten), while the most-recent keys still report true.
    - Touch-on-hit ordering: a key re-seen via SeenOrAdd is moved to most-recently-used, so it survives an eviction that would otherwise have removed it.
    - Len() reports current entry count and never exceeds capacity.
  </behavior>
  <action>
    Create package `dedup`. Implement `LRU` backed by `container/list` (a doubly linked list, most-recently-used at Front) plus `map[[32]byte]*list.Element`. Key type is `[32]byte` (the decoded 32-byte event ID) — half the memory of the 64-char hex string. Element value stores the key so eviction can delete the map entry for the popped Back element.

    Methods:
    - `New(capacity int) *LRU` — store capacity; if capacity <= 0 treat as disabled (SeenOrAdd is a no-op returning false; do not allocate growth).
    - `SeenOrAdd(key [32]byte) bool` — if capacity<=0 return false. If key present: move its element to Front, return true. If absent: push key to Front, insert into map; if Len() > capacity, remove Back element and delete its map entry; return false.
    - `Len() int` — number of tracked keys.

    Document at the package/type level that LRU is NOT safe for concurrent use and is designed for a single-goroutine caller (the bloom plugin's sequential stdin event loop), mirroring the lock-free single-writer contract documented in pkg/bloomgate/checker.go. Do NOT add a mutex. Do NOT add any new module dependency — container/list is stdlib.

    Write lru_test.go covering every case in <behavior> above, using distinct [32]byte keys (e.g. build keys with a helper that sets one byte to an index).
  </action>

  </verify>
